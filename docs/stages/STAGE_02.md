## 2. What are we building?

Typed **Pydantic schemas** and **SQLAlchemy ORM models** for the enterprise portfolio, plus **Alembic** migrations so the database schema is versioned.

Entities include: Project, Application, Service, DatabaseAsset, ApiAsset, InfrastructureResource, Technology, Dependency, Document, DocumentChunk, Evidence, Risk, MigrationRecommendation, Approval, MigrationWave, CostEstimate, AuditEvent.

## 3. Why are we building it?

Without a shared data model, every later engine (graph, risk, cost, AI) invents its own meaning of “application.” The LLM must not be the database.

## 4. What problem does it solve?

Ambiguous portfolio language and no durable system of record. Stage 2 gives one vocabulary for APIs, persistence, and future AI structured outputs.

## 5. Concepts I need to understand first

### Pydantic schema

**Simple:** A Python class that describes valid data shapes. Bad data errors immediately.  
**Interview:** Shared contracts for API payloads and (later) LLM structured outputs.

### ORM model

**Simple:** Object-Relational Mapper — Python classes mapped to tables.  
**Interview:** We work with `Application` objects while Postgres stores rows.

### Alembic migration

**Simple:** Versioned scripts that change schema safely (like git for tables).  
**Interview:** Local, CI, and Azure stay aligned via `alembic upgrade head`.

### Primary key / foreign key

**Simple:** PK uniquely identifies a row; FK must point to a real related row.  
**Interview:** Stops orphan graph edges once Stage 4 enforces inventory integrity.

### External ID vs UUID

**Simple:** UUID is the internal database key; `external_id` like `APP-PAY-001` is the business citation ID used in evidence and CSVs.  
**Why:** Humans and AI cite stable business IDs; UUIDs stay internal.

## 6. Technologies used

### Pydantic v2

- **What:** Validation library  
- **Why:** One schema language for API + AI  
- **How:** `app/schemas/inventory.py`, `app/schemas/analysis.py`

### SQLAlchemy 2.x

- **What:** ORM / SQL toolkit  
- **Why:** Typed models and relationships  
- **How:** `app/models/*`

### Alembic

- **What:** Schema migrations  
- **Why:** Reproducible database evolution  
- **How:** `alembic/`, revision `d5df7dcba761_initial_enterprise_schema.py`

### PostgreSQL

- **What:** Relational database  
- **Why:** System of record (JSONB/ARRAY for flexible fields)  
- **How:** Tables created and used by integration tests

## 7. Architecture

```
Pydantic schemas (API / validation contracts)
        ↕ from_attributes
SQLAlchemy models (relationships, constraints)
        ↓
Alembic migration
        ↓
PostgreSQL tables (system of record)
```

Dependency edges use `asset_type + external_id` (not a single polymorphic FK) so the graph can span apps, services, DBs, APIs, and infra. Stage 4 will validate that referenced IDs exist.

## 11. Failure scenarios

- Duplicate `(project_id, external_id)` for applications → integrity error  
- Invalid enum / confidence out of range → Pydantic `ValidationError`  
- Missing `project_id` FK → database rejects child row  
- Orphan dependency external IDs → allowed at DB layer today; caught in Stage 4 quality checks

## 12. How we handle failures

- Pydantic validates at the boundary before persistence  
- DB unique/FK constraints as last line of defense  
- Integration tests assert `IntegrityError` on duplicates  
- Dependency referential checks deferred to ingestion (documented tradeoff)

## 13. Important engineering decisions

- **DatabaseAsset** name avoids clashing with `app.database` package  
- Polymorphic dependency endpoints via type + external_id (graph-friendly)  
- Document chunks store `evidence_id` now; **embedding column deferred to Stage 6**  
- Cost/recommendation tables exist early so later engines write into a stable schema  

## 14. Alternatives

| Alternative | Why not |
|-------------|---------|
| Only Pydantic, no ORM | No durable system of record |
| MongoDB document store | Weaker relational integrity for portfolio graphs |
| Strict FKs for every dependency endpoint | Painful across heterogeneous asset types |
| Embeddings in Stage 2 | Premature; Stage 6 owns RAG |

## 17. Interview answers

1. “Pydantic validates in-memory data shapes; ORM maps objects to tables.”  
2. “Postgres is the system of record — auditable, queryable, shared by all engines.”  
3. “UUID for joins; external_id like APP-017 for human/AI citations.”  
4. “Dependencies store source/target asset type plus external IDs so edges can span heterogeneous assets.”  
5. “Unique constraints reject duplicates; quality pipeline will also flag them.”  
6. “Add tenant_id to Project and scope uniqueness per tenant; keep the same module boundaries.”
